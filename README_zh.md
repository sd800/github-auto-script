# Auto Script for GitHub Setup and Push

[English](README.md)

Auto Script for GitHub Setup and Push 是一个面向所有人的集中式 Bash 工具，用更少操作把本地改动上传到 GitHub，同时让每个仓库始终使用一个明确账号和一把指定密钥。精简的 `git-auto.sh` 负责加载 `src/` 中的中央实现，每个项目则使用同一套简洁的 `g.sh` 操作入口。

快速、方便、简洁是本项目的基本原则。日常上传就走日常流程；只有缺少信息或配置发生变化时，才进入详细引导，严禁把简单问题复杂化。

日常只需记住四个入口：

- `./g.sh`：使用当前项目已经保存的所属账号和密钥，暂存改动，按版本号自动提交，并上传。
- `./g.sh new`：添加 GitHub 账号及其本机 SSH 密钥，并可继续用于当前项目。
- `./g.sh update`：GitHub 用户名或仓库名已经改好后，同步本机设置。
- `./g.sh menu`：打开项目本机设置、偏好选项和高级诊断工具。

SSH 身份、账号核验、项目提交身份、发布提交说明、上游分支和严格推送身份均由脚本在内部处理。

## 技术实现原则

“快速、方便、简洁”同时也是技术实现规范。普通命令只采用能够正确完成任务的最少 Git 与 SSH 操作：本机已有完整状态就直接复用；依赖只在具体功能确实需要时检查；安全控制优先使用 Git 自身的原子机制，不重复增加前置流程。`ssh -T`、`git ls-remote` 和现有账号识别等可选联网检查统一放在“高级功能”中。日常上传在必要的 `git push` 之前不会额外联网。可能耗时的阶段会明确说明正在处理什么，上传时直接显示 Git 提供的真实传输进度，不隐藏输出，也不编造虚假的百分比。Git 输出不会打开交互式分页器；已经建立的 SSH 连接如果持续无响应，也会通过存活检查及时返回控制权。

## 整体结构

整个项目由一套模块化中央程序、一份私人配置和每个项目各自的启动器组成：

```text
git-auto/
|-- git-auto.sh       精简的中央调度入口
|-- g.sh              公开且可以直接复制的轻量启动器
|-- VERSION           当前发布版本号
|-- src/              中央 Bash 实现
|   |-- 00-core.sh
|   |-- 10-ssh.sh
|   |-- 20-repository.sh
|   |-- 25-safety.sh
|   |-- 30-workflow.sh
|   |-- 40-history.sh
|   |-- 50-update.sh
|   |-- 60-menu.sh
|   `-- option.txt      纯技术开关配置；当前为空
|-- README.md
|-- README_zh.md
|-- CHANGELOG.md
|-- CHANGELOG_zh.md
|-- tests/
|-- sidenote/         本机 Agent 笔记；不会进入 Git
`-- private/          仅保留在本机；自动创建且不会进入 Git
    |-- config.txt    个人偏好与账号资料
    `-- g.sh          已写入中央路径、可直接复制的启动器

your-project/
|-- g.sh              自动生成的轻量启动器；仅保留在本机
`-- 项目文件...
```

`git-auto.sh` 只负责定位并加载同目录下的必要模块。各模块分别承载配置与界面、SSH 身份、仓库地址识别、日常上传、历史导入、改名同步和菜单入口。缺少任何模块时，程序会在流程开始前停止，并明确指出缺少哪个文件。

`git-auto.sh` 与 `src/` 共同组成一套中央安装，移动或复制时应当保持在一起。整套程序仍然是无需安装软件包的自包含 Bash 代码；不再区分公开脚本和个人脚本，也不在可执行代码中重复保存账号区块。中央程序更新一次，所有启动器都会使用新功能。

根目录的 [`VERSION`](VERSION) 文件单独记录本项目当前的发布版本号。每次发布时，它与中英文变更日志同步更新。

## 第一次使用

把公开项目放在准备长期保存中央脚本的位置，然后运行：

```bash
chmod +x git-auto.sh
./git-auto.sh
```

第一次在交互式终端中运行时，脚本会询问一次界面语言，并把选择写入 `private/config.txt`。中央管理菜单可以把 `g.sh` 复制到指定项目；程序还会生成已经写入中央脚本位置的 `private/g.sh`。需要手动复制时，最省事的方式是：

```bash
cp private/g.sh /path/to/your-project/g.sh
```

根目录由 Git 跟踪的 `g.sh` 仍是提供给其他用户和其他安装位置的通用公开版本。

以后进入具体项目，只使用下面四个短命令：

```bash
./g.sh
./g.sh new
./g.sh update
./g.sh menu
```

不需要设置 Shell alias、修改 PATH、安装软件包，也不会创建额外的应用专用用户配置目录。需要提交和上传中央仓库本身时，直接运行其中由 Git 跟踪的 `./g.sh`。

## 中央管理菜单

在中央文件夹中运行 `./git-auto.sh` 会打开管理菜单，可用于：

- 为指定项目创建或修复 `g.sh`。
- 把 GitHub 账号添加到共享私人配置。
- 修改所有项目共用的界面语言和显示模式。
- 按需执行现有 SSH 账号、已保存密钥和当前项目的联网诊断。
- 进入高级工具，包括历史发布版本导入。

在中央文件夹中运行 `./git-auto.sh new` 可以直接进入账号设置。直接运行 `./git-auto.sh` 只负责中央管理；所有项目操作都使用 `./g.sh`，中央仓库本身也不例外。

## 轻量级项目启动器

公开的 `g.sh` 不包含 GitHub 账号、SSH、版本、提交或历史重建业务逻辑。它会把自身所在文件夹作为项目根目录，并直接使用该仓库本地 Git 设置中保存的中央脚本路径。中央仓库自己的 `g.sh` 也可以直接使用同目录下的 `git-auto.sh`。这两个准确位置都不存在时，启动器才会询问 `git-auto.sh` 文件或其所在文件夹的路径，不会扫描无关目录。

项目文件夹可以位于另一个 Git 仓库里面。如果它还没有自己的 `.git`，正常配置流程会在该文件夹创建独立的嵌套仓库，不会把启动器绑定到外层仓库；仅检查命令不会初始化子仓库。

`g.sh` 是可以长期保留在项目中的种子启动器。把这个版本复制到项目后，日常版本更新无需再替换它：新增功能、界面文案和安全逻辑全部来自中央 `git-auto.sh` 与 `src/`。因此只要更新中央项目，所有已经连接的项目就会同时使用新版本。启动器还会传递固定的协议标记，让以后更新的中央引擎继续兼容这份种子文件。

中央仓库根目录的 `g.sh` 由 Git 正常跟踪，绝不会加入该仓库的忽略规则。中央菜单把它复制到其他项目后，只会将那个项目中的副本写入 `.git/info/exclude`，不会改动团队共享的 `.gitignore`。项目完成配置后，中央脚本路径保存在该项目自己的 `.git/config` 中；`g.sh` 本身不含任何个人路径。

中央文件夹移动后，原有启动器会询问新的文件夹路径或完整 `git-auto.sh` 路径，并把它保存在当前仓库本地；`g.sh` 文件本身仍然不用修改。也可以从中央菜单修复保存的路径。运行中央管理程序或中央仓库自己的 `g.sh` 时，还会用当前位置刷新被忽略的 `private/g.sh`；其他项目日常上传时不增加额外维护操作。

## 私人配置

所有个性化应用状态都保存在 `git-auto.sh` 旁边被 Git 忽略的 `private/config.txt`：

```text
language: zh
display-theme: auto

username: johnjoe
email: 123456+johnjoe@users.noreply.github.com

username: alice
email: alice@example.com
```

每个字段独占一行，账号之间用空行分隔。每个账号只有 GitHub 用户名和提交邮箱，提交显示名始终由 GitHub 用户名自动确定。

`display-theme` 继续保存在这份私人配置中，因为它是多值显示偏好，并非单纯的开启或关闭开关。

需要长期保存的二元开关只能写入 `src/option.txt`：每行使用一个固定技术标签，值只能是 `enabled` 或 `disabled`。当前版本没有需要保存的二元开关，因此 `src/option.txt` 特意保持为空；其中不写入用户资料或说明文字。

中央引擎会自动创建 `private/`，并把目录和配置文件权限分别限制为只有当前用户可以访问和读写。保存时采用原子替换，不会在其中写入私钥、密钥口令、访问令牌或登录密码。

其他人使用公开项目时，也会自动得到各自独立且被忽略的 `private/` 文件夹。其中生成的 `g.sh` 只负责预置该用户自己的中央脚本位置；账号和偏好字段仍然只保存在 `config.txt`。

## 输入方式

- 菜单不超过 8 项时，使用 `1` 至 `8`。
- 列表超过 8 项后，前 8 项仍使用数字，后续依次使用 `a b c d e f g h j k m n p r`。GitHub 账号会先按用户名排序，排序时不区分大小写，再分配这些选项。
- 列表超过一页时，按 `x` 查看上一页，按 `y` 查看下一页。`s` 和 `w` 留给未来功能；`i`、`l`、`o`、`q`、`t`、`u`、`v` 不会用作选项。
- 账号不超过 8 个时，“添加另一个账号”使用 `9`；超过 8 个后改用 `z`。
- `0` 始终列在最后；输入 `0` 即可返回或取消，不会选中任何一项。
- 只需确认是否执行某项已经说明清楚的操作时，界面会直接询问“是”或“否”，无需记忆额外的数字含义。

## 运行 g.sh 后会发生什么？

默认流程完全依据项目当前状态推进：

1. 把 `g.sh` 所在文件夹作为准确的项目根目录。
2. 首先判断这里是否已经是 Git 仓库。若已经初始化，现有提交、分支、暂存内容和远端设置全部保留，也不会再次执行 `git init`。若尚未初始化，脚本会先说明 `git init` 此时只创建本地记录，再执行初始化。
3. 在完整流程期间锁定当前 Git 仓库。第一个 `g.sh` 结束前，另一个 `g.sh` 不能同时为同一仓库准备暂存内容、创建提交、修改绑定或执行上传。
4. 如果当前处于 detached HEAD、仍有未解决冲突，或 merge、rebase、cherry-pick、revert 尚未完成，立即停止，不修改项目文件。
5. 读取 `origin`，确定准确的 GitHub `owner/repository`。只有 `origin` 无法识别目标仓库时，才询问仓库地址。
6. 只有仓库所属账号、提交名称、邮箱、SSH 主机名、指定私钥以及 `origin` 的拉取和推送地址全部一致时，才直接进入快速流程；否则只修复缺失或不一致的本机设置，不会提前联网核对。
7. 只使用与仓库 owner 同名的账号，并固定使用该账号在本机指定的一把 SSH 密钥。其他账号和普通 `github.com` 默认密钥都不会成为备用身份。
8. 按当前暂存区中的跟踪记录重新建立独立 Git index，不沿用缓存的文件时间，再按 `git add -A` 的规则扫描工作区。这样既能保留用户主动暂存的忽略文件、已暂存的删除和稀疏检出范围，也能找出被 index 提示隐藏的改动。程序会完整记录准确的待提交清单，供用户确认；终端最多列出前 25 个文件，超出时标明总数和省略数量。此时不会改动真实暂存区。
9. 用户确认提交说明后，再次核对仓库、分支、HEAD、origin、账号绑定、Git index、文件内容和未跟踪文件集合，然后执行 `git add -A`。真实暂存树以及最终生成的提交，必须与确认过的文件、提交说明和账号身份完全一致，随后才会把这个准确提交对象发送到 `origin` 上明确指定的当前分支。如果本次没有创建提交，程序会显示最新本地提交说明，并在连接 GitHub 前另行取得确认。
10. SSH 身份验证、现有账号识别和仓库只读检查等可选联网操作统一放在“高级功能”中。
11. 如果 push 失败，本地提交会完整保留，并根据 GitHub 的实际返回结果说明是远端历史不一致、账号或仓库被拒绝、网络中断，还是其他 Git 错误。如果 GitHub 上存在本机没有的提交，程序会提供一个默认选择“否”的选项：保留两边历史，再把当前本机版本作为最新完整快照追加到上面。普通上传绝不强制覆盖。

工作区没有改动时不会制造空提交。程序不会单独采信空白的 `git status`；只有独立完整扫描得到的文件树也与 `HEAD` 完全一致，才能认定没有改动。即使快速状态同时遗漏一个或多个跟踪文件，内部完整清单仍会把它们和普通改动一起纳入核对，不受终端显示数量限制；干净的稀疏检出也不会被误判为删除文件。如果暂存区和工作区中的改动正好相互抵消，程序会保持原有暂存状态并停止。工作区确实没有改动但本地已有提交时，`./g.sh` 会明确标出提交说明并询问是否继续上传。仓库既没有提交也没有项目文件时会直接结束；在提交说明处取消也发生在暂存之前。

如果文件夹已有 Git 记录但无法正常打开，程序会直接停止，不会重新初始化。连续执行多个 cherry-pick 或 revert 时，即使其中一次冲突已经解决并提交，只要整组操作还没结束，也不能继续普通上传流程。无论位于哪一层目录，新加入但未登记为子模块的嵌套 Git 仓库都会被拦截；已经正确登记的子模块可以正常使用，子模块检查失败也不会被当作“没有改动”。

用户确认的提交说明会原样保留，包括开头的 `#`，不会被 Git 的提交说明清理设置删掉。普通文件提交仍会照常执行 Git hook；如果 hook 改写了已确认的说明或文件内容，程序会停止自动上传。

如果 GitHub 因远端分支包含本机没有的提交而拒绝上传，程序首先会保持两边原状，随后提供一次可选的恢复操作，默认选择“否”。选择“是”后，程序会读取远端最新分支，并再次展示衔接提交的说明供用户确认。远端历史会保留在主线上，本机原有历史也会作为另一条父历史保留；新生成的最新提交则采用当前本机版本的完整文件树。重试仍是普通的 fast-forward 上传，不删除远端提交、不使用强制推送，也不会通过自动解决冲突来改动文件。在任一确认处取消，都不会改动两边历史。

## GitHub 账号设置

在能够识别 GitHub `origin` 的项目中，`./g.sh new` 会直接从仓库 owner 确定必须使用的用户名，不再让用户选择其他账号。离开具体项目后，中央账号菜单仍可添加任意个人账号。普通设置遵循以下规则：

1. 在具体项目中，如果仓库所属账号尚未保存，只询问该账号的提交邮箱。
2. 按照固定顺序沿用身份：当前项目保存的完整准确绑定优先，其次是中央仓库为同一所属账号保存的完整绑定，最后才采用 `github-USERNAME` 形式的主机名。如果项目保存的 SSH 主机名已经删除或改指其他密钥，但项目保存的准确原密钥仍在，脚本会为这把原密钥补建不冲突的用户名式主机名，不会再创建一把密钥。
3. 如果电脑中已有其他 GitHub 密钥，但仅凭本机名称无法确定哪一把属于当前账号，脚本不会猜测，也不会默认再建一把；用户可以明确选择高级联网识别、明确选择新建，或者退出。
4. 确实没有可沿用的本机 GitHub 身份时，先明确显示将增加的密钥路径和 SSH 主机名，再创建独立的 ED25519 密钥。
5. 引导用户把公钥添加到正确的 GitHub 账号，然后保存本机账号与密钥的对应关系。
6. 除非用户明确选择高级身份识别，普通流程不执行 `ssh -T` 或仓库只读预检；以后上传时，由 `git push` 返回 GitHub 的实际结果。

新 SSH 主机名默认使用 `github-USERNAME`。遇到冲突时会自动尝试 `-1`、`-2` 及后续数字。每个新建账号使用不同私钥。需要补写准确主机名时，脚本会保留采用软链接的 `~/.ssh/config`，正确处理密钥路径，并在保存前确认该主机名最终选中的确实是指定文件。“高级功能”会检查明确写出的 SSH 主机、`Include` 和通配规则继承的设置、`github.com` 的实际默认连接、这些连接列出的每一把现有密钥，以及尚未分配给任何主机的常见 `~/.ssh/id_*` 私钥；随后可由 GitHub 返回各密钥对应的实际账号，并把确认后的身份导入到稳定的用户名式 SSH 主机名下。核对过程采用非交互连接，密钥尚未解锁或无法使用时会直接返回，不会突然停下来索要密钥口令。

本机默认建议为 `USERNAME@users.noreply.github.com`。也可以改成 GitHub 页面显示的准确隐私邮箱，包括 `ID+USERNAME@users.noreply.github.com` 格式，或者该账号已经验证的其他邮箱。

## 多账号保护

共享私人配置让所有项目都能找到已经配置好的账号，但每个仓库只能使用与仓库所属用户名一致的那个账号。

项目专属信息只保存在该仓库的 `.git/config`：用户名、邮箱、SSH 连接名、密钥文件，以及规范化后的 `origin` 拉取与推送地址。只有这些内容彼此一致，才属于完整绑定。每次网络操作前，脚本都会创建临时 SSH 包装程序，启用 `IdentitiesOnly=yes` 并固定选定私钥，SSH Agent 中的其他密钥不能静默成为备用身份。

当前流程会严格检查账号与仓库 owner 是否同名。如果 `owner/repository` 属于另一个用户名，脚本会直接停止；即使某个账号能够读取公开仓库，也不会因此把它绑定到该仓库或用于上传。

普通命令信任已经明确保存的本机账号与密钥对应关系，并在 `git push` 时接收远端结果。遇到旧式或人工命名的 SSH 主机时，可以使用高级联网诊断确认它实际登录的 GitHub 用户名；确认后会自动增加稳定的用户名式主机名，同时保留旧配置。

每次上传时，`origin` 最终生效的推送地址必须只有一个，并且与所选账号和仓库一致。如果其他 Git 配置文件或地址重写规则增加了额外目标，程序会停止上传。程序自己的 Git 命令还会临时关闭镜像推送、自动附带标签和递归推送子模块，只上传本次明确指定的分支，不改动用户保存的相关设置。

## 仓库地址输入

仓库输入框可以识别并规范化常见 GitHub 格式：

```text
owner/repository
owner/repository.git
github.com/owner/repository
https://github.com/owner/repository
https://github.com/owner/repository/tree/main
https://github.com/owner/repository/blob/main/README.md
git@github.com:owner/repository.git
ssh://git@github.com/owner/repository.git
git://github.com/owner/repository.git
git clone https://github.com/owner/repository.git
gh repo clone owner/repository
```

查询参数、页面锚点、末尾斜杠、`.git` 和仓库内部页面路径都会自动去除。非 GitHub 地址会被明确拒绝，不会静默改写。

## 用户名或仓库发生变化

在 GitHub 上完成用户名修改或仓库改名后，在受影响项目中运行 `./g.sh update`。

这个流程以 GitHub 上已经完成更名为前提。脚本先询问哪项内容发生了变化，只收集相关的新信息，并始终让仓库 owner 与账号用户名保持一致；如果粘贴了其他账号名下的仓库地址，会要求重新输入。写入前会逐项列出即将修改的本机文件和 Git 设置。

用户名变化时继续使用原密钥；需要新 SSH 主机名时自动生成无冲突的用户名形式，同时保留旧主机名，避免影响其他项目。脚本还会同步共享私人账号记录、当前仓库的提交身份和 `origin` 拉取与推送地址。整个 update 流程不会修改或上传项目文件、分支、提交记录和 GitHub 远端仓库；在最终确认处取消时，`private/config.txt`、`~/.ssh/config` 和当前仓库的 `.git/config` 都保持不变。

`update` 全程不会联网。下次正常执行 `git push` 时，再确认更名后的账号和仓库；如果希望单独进行 SSH 或仓库只读诊断，可从“高级功能”中明确选择。

## 提交说明和发布版本

脚本创建任何正式提交前，都必须先取得用户确认。对于已经完成设置的项目，`./g.sh` 仍保持简洁流程：先预览执行 `git add -A` 后实际会得到的准确文件快照，检查是否意外混入了另一个项目，再同时列出本次建议的提交说明和本机为该 GitHub 分支记录的上次提交说明，随后请用户确认。这里直接使用成功上传后更新的本机远端分支记录，不会为了显示这一行而增加提交前联网检查。确认后，程序依次执行 `git add -A`、`git commit` 和 `git push`。直接按 Enter 即可采用建议内容，也可以输入其他说明；输入 `:cancel` 会在暂存前停止。工作区没有改动时会跳过 commit，明确标出最新本地提交说明，再用简短问题询问是否上传。

只要工作区存在改动，每次提交都会先完整检查待提交文件；终端最多显示前 25 项，超出时标明总数和省略数量。省略的只是终端明细，实际核对与提交仍覆盖所有文件。超过 25 个文件时，Git 创建提交后的逐项文件输出也会省略，不会打开交互式分页器。如果一个从未出现在当前历史中的新增目录包含 `package.json`、`pyproject.toml`、`Cargo.toml` 或 `go.mod` 等项目标志，脚本会列明目录和依据，并增加一次默认选择“否”的确认。完全新增且包含 20 个或更多文件的顶层目录也会进行同样检查。如果某个文件夹包含自己尚未登记的 `.git` 目录，程序会直接停止，因为 Git 只会记录仓库链接，并不会把其中的普通文件内容纳入当前项目。已经配置为子模块的目录若还有未提交改动，也必须先在子模块内部完成提交。规模较小的普通新增文件夹不会增加询问。

首次提交只要识别到有效版本，也会建议对应的提交说明，例如 `Release 1.2.3.4`；后续提交即使版本号没有变化，通常仍可沿用。版本号允许两段及以上用点分隔的数字，不限于三段。唯一的例外是 `package.json` 中未发生变化的常见脚手架占位版本：`0.0.0`、`0.0.1`、`0.1.0` 或 `1.0.0`。这些值第一次加入项目或后来确实被改成该值时仍然有效；只有原样保留的占位版本不会覆盖更可靠的版本来源，也不会取代正常的备用提交说明。

根目录的 `VERSION` 最优先。只有根目录找不到可用版本时，程序才检查所有直属子文件夹中的文件；不会继续深入孙级目录。根目录的 CHANGELOG 一旦找到有效版本，也不会再检查子文件夹。CHANGELOG 和子文件夹的查找最多进行 5 秒；如果仍未完成，程序会询问是否手动填写版本号。直接按 Enter，提交说明就保持为 `Initial commit` 或 `Update`。查找顺序如下：

1. 根目录 `VERSION`，然后是根目录 `VERSION.txt`、`VERSION.md` 和其他 `VERSION*` 文件。
2. 根目录 `package.json` 中的有效版本。
3. 根目录的项目元数据：`manifest.json`、`manifest.webmanifest`、`pyproject.toml`、`Cargo.toml`、`composer.json`、`pubspec.yaml`、`deno.json` 和 `bower.json`。
4. 根目录的 `CHANGELOG*`，包括各语言版本；若有多个有效版本，采用其中最高的版本。
5. 所有直属子文件夹中的文件：先查 `VERSION*`，再查 `package.json`、上述元数据格式，最后查 `CHANGELOG*`。同一类文件取最高有效版本；`VERSION`、`VERSION.txt` 等仍按文件名优先级查找。
6. 第一次提交回退为 `Initial commit`，后续提交回退为 `Update`。

解析支持新版本在顶部或底部、常见英文和中文日期、预发布版本、构建信息、可选 `v` 前缀、方括号和多种 Unicode 破折号。查找直属子文件夹时会排除 Git 元数据、依赖、缓存、虚拟环境和覆盖率目录。

## 导入历史发布版本

高级菜单可以从一组完整版本文件夹重新建立原本缺失的线性 Git 历史。

脚本会发现或接收版本映射，按版本号各段数字从旧到新排序，并在临时仓库中为每个版本创建一个完整的 `Release <version>` 快照提交。新版已经删除的旧文件不会残留在新版快照中。正常隐藏文件和被忽略文件会保留，每一层的 `.git` 和 `.DS_Store` 都会排除。

存档版本缺少根目录 `.gitignore` 时，用户可以在终端直接粘贴一份通用规则。它只会添加到缺失的重建快照，不会写回原始版本文件夹。

流程会检查疑似敏感文件和超大文件，展示 `git log --oneline --reverse`，并在上传前验证选定的 GitHub 身份。文件安全检查和快照构建会显示 `[当前项/总数]`，上传时会实时显示 Git 的真实传输进度。默认使用可靠识别到的发布日期重建提交时间；用户可以选择不写入历史日期，此时每个提交保留 Git 创建它时自动记录的本机时间。

创建重建提交之前，版本计划会逐项显示准确的 `Release <version>` 提交说明。用户只需对整份已列明的历史确认一次；没有取得这次确认时，内部构建程序连第一个提交也不会创建。

替换已有远端 `main` 必须明确确认，并使用精确的 `--force-with-lease`。脚本不会创建备份分支，也不会改动其他远端分支。历史重建只创建版本提交，不创建或修改 Git 标签。

上传完成后，流程会询问是否把重建后的 `main` 衔接到现有且通常并非空白的日常工作目录。脚本不会复制覆盖、删除或替换当前项目文件。目录还没有 Git 记录时才执行 `git init`；已有但与重建记录无关时，会先说明影响并取得确认。随后使用 mixed reset 只移动分支历史，把当前文件与最后一个历史版本之间的差异保留为普通未提交改动。最后写入轻量 `g.sh` 以及所属账号、密钥和 origin 绑定，之后可直接运行 `./g.sh` 提交并上传当前工作。

快照复制由中央引擎自行实现，不依赖 `rsync`。

## 语言、显示和无障碍体验

第一次运行默认选择英文，也可使用完整本地化的中文界面。选定语言统一应用于项目命令、中央管理、更新流程、高级工具、说明、提醒和错误信息，并可从任一菜单修改。

显示模式支持自动、深色、浅色和无颜色。自动模式优先读取终端背景信息，在 macOS 上也会参考系统外观。设置 `NO_COLOR` 或非交互输出时会关闭颜色。

整个界面只使用纯文字状态标签，不输出 Emoji 表情符号。

## 安全与本机状态

中央引擎只写入当前流程确实需要的位置：

- `private/config.txt`：共享的个人偏好与账号基本资料。
- `private/g.sh`：包含当前中央脚本位置、可直接复制且不会进入 Git 的启动器。
- `src/option.txt`：需要长期保存的二元技术开关；当前为空。
- `~/.ssh`：GitHub SSH 密钥和配置。
- 目标仓库的 `.git/config` 与 `.git/info/exclude`：本地账号绑定和启动器排除。
- 临时目录：严格 SSH 包装程序和历史版本重建仓库。

脚本不会使用其他应用专用配置目录。只有当前所选流程确实需要处理 SSH 身份时，才会创建或修改 `~/.ssh`，并且会在创建前明确显示新增私钥和主机名。私钥不会复制到中央项目或 `private/config.txt`。程序会清除外层终端继承进来的 Git 仓库、index、对象存储和提交身份覆盖设置，避免启动器或中央引擎被指向其他项目或错误账号。普通命令不执行可选联网预检，普通推送绝不使用强制覆盖，历史导入也始终保持原始发布文件夹不变。

## 运行要求和测试

- Bash 3.2 或更高版本。
- Git 与 OpenSSH；只有确实需要新建密钥时才要求 `ssh-keygen`。
- 模块化 Bash 引擎使用的标准 POSIX/macOS 工具。
- 执行 `git push`，以及用户主动选择高级联网诊断时，需要能够连接 GitHub。

运行隔离测试：

```bash
./tests/test.sh
bash tests/test.sh --commit-confirmation
bash tests/audit-regressions.sh
```

测试使用临时用户目录、私人配置、Git 仓库、SSH 配置和模拟 SSH 传输，覆盖快速上传、完整设置、账号隔离、版本提交、上传失败说明和远端历史保留；不会读取真实私人配置，也不会改动真实 GitHub 仓库。
